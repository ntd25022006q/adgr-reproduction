\section{Terminology conventions}
This report keeps the English technical terms, each with a short gloss in
parentheses on first use. Every number comes from the real result file
(\texttt{FINAL\_v2.json}) --- no estimates, no beautified rounding.
\begin{itemize}[leftmargin=*]
\item \textbf{chunk} (a text passage; here one article section is one chunk).
\item \textbf{entity} (a drug, disease, symptom name...),
\textbf{relation} (an entity pair plus its described link).
\item \textbf{knowledge graph (KG)} (the entity--relation network).
\item \textbf{Hit@K} (share of questions answered correctly in the top K),
\textbf{MRR} and \textbf{nDCG@10} (rank-weighted measures: higher ranks score
more).
\item \textbf{RAGAS} (the 4-metric RAG quality suite),
\textbf{faithfulness} (how closely the answer follows the context),
\textbf{answer relevancy} (fit to the question),
\textbf{context recall} (does the context cover everything needed),
\textbf{context precision} (is the context lean and noise-free).
\item \textbf{ablation} (disabling exactly one module to measure its
importance).
\item \textbf{anchor} (an entity foothold for expanding search),
\textbf{edge filter} (the noisy-edge filter),
\textbf{rerank/reranker} (re-scoring and re-ordering candidates).
\item \textbf{DSER / SCR / LCR} (share of in-domain entities / valid relations
/ entities inside the giant connected component).
\item \textbf{standalone} (a model answering bare, without RAG),
\textbf{judge} (the scoring model).
\end{itemize}

\section{Work done, stage by stage (with the hard part each)}
\begin{itemize}[leftmargin=*]
\item \textbf{Corpus:} crawled 1,934 medical articles (5 dead URLs, 4 rescued
via alternate sources, 1 dropped with a written record). Hard part: 429
rate-limits forced retries spread over many hours.
\item \textbf{Chunking:} the authors' H2 code (\texttt{thesis\_src}), so the
algorithm matches; 15,837 chunks (min 126, median 800, mean 1,129 chars,
$\sim$357 tokens). 8\% missing from 5 dead URLs + doc filtering. Hard part:
the chunker is not released with the paper, so this pipeline step depends on
external code (documented in the README).
\item \textbf{KG:} Qwen2.5-14B temp 0 over every chunk $\rightarrow$ 52,578
entities / 106,279 relations (paper: 49,274 / 106,666); 3.3 distinct entities
per chunk on average (densest chunk: 171 extraction hits). Hard part: 15,837
chunks through a GPU for tens of hours with occasional malformed outputs;
per-chunk checkpoints plus defensive parsing meant a crash cost exactly the
chunk in flight.
\item \textbf{Retrieval:} 300 questions $\times$ 5 arms (full + 4 ablations,
each disabling exactly one module per Sec.~5.8) + 2 LightRAG baselines with
rerank off per Sec.~5.2. Hard part: one GPU shared four ways (vLLM + ollama +
reranker + someone else's 4.4GB training job), hence a per-stage VRAM budget,
maxlen cuts, CPU keyword extraction, and keyword memoization (1 call per
question instead of 5).
\item \textbf{Scoring:} Hit/MRR/nDCG (dual gold proxies); the 4 RAGAS
components implemented from the original formulas; 4 dims $\times$ 5
independent judge runs; per-row tokens and latency. Hard part: one dead API
key silently poisoned 123 rows before detection --- since then every judge
function carries a quota guard: a dead key halts loudly
(\texttt{os.\_exit(42)}), never marking a failed row ``done''.
\item \textbf{Quality control:} per-question checkpoints (a crash loses
$\le$1 row); a validation gate after each stage (bad numbers exit 99 loudly,
8 boundaries); every fix verified on the machine with evidence (43 bugs total).
\item \textbf{Resource budget (measured):} three verified vLLM profiles
(32k/0.72; 12k/0.62; 8k/0.50 with maxlen 8192; KV 1.91GB $<$ 2.25GB forced the
12k maxlen down to 8192); one GPU split four ways, so keywords come from CPU;
Solar caps at 100 req/min, so judging escalates minimal x3 $\rightarrow$ low
x1 (116 vs 3,273 tokens, 28x cheaper); 429s are retried and failed runs never
count toward $n$ (\texttt{tab5\_5run} pattern).
\end{itemize}

\section{Similarities and deviations vs the paper (complete list)}
Matches and deviations are all disclosed; none is hidden in the numbers.
\begin{itemize}[leftmargin=*]
\item \textbf{MATCHES paper Sec.~5.1 (not substitutions):} Qwen2.5-14B-Instruct
-AWQ for generation and KG extraction, \texttt{embeddinggemma:300m} embedding
(768-dim), Qwen3-Reranker-0.6B reranker, vLLM, temp 0 --- same models, same
settings. Only the vector store differs (ours: numpy matrices + BM25; paper:
NanoVectorDB) while the embedding vectors are identical, so lookup is
equivalent.
\item \textbf{Judge:} solar-pro4 instead of GPT-5.5 (no GPT-5.5 API access; its
strictness was measured via the original-prompt cross-check in Table 5).
\item \textbf{Gold labels:} the authors' manual gold $\rightarrow$ two proxies:
slug-gold (optimistic: correct = a chunk from the same article) and
single-gold (pessimistic: correct = the single most similar chunk). Without
hand-made labels, paper numbers are never impersonated; both scales reported.
\item \textbf{Standalone:} the paper's 7 paid models $\rightarrow$ 7 free models,
zero overlap (reference points only, never ranked against the paper).
\item \textbf{Chunker USES the authors' H2 code} (\texttt{thesis\_src}, outside
the repo, not redistributed): 91.9\% match by count; the missing 8\% comes from
5 dead URLs + doc filtering (only docs with $>$200 chars of markdown kept) ---
input data differs, the algorithm does not. Measured consequences: $\sim$9.4
extraction hits/chunk (Figure 3) and lower LCR.
\item \textbf{RAGAS:} reimplemented from the published formulas instead of the
official library (to share the solar judge and control cost; standard RAGAS on
300 samples, of which ctx.rec. has data for 275 and ctx.prec. for 46; formulas
cross-checked).
\item \textbf{One-step faithfulness} instead of the standard two-step (far
cheaper; impact measured on identical data: 0.41 vs 0.77 --- both reported, see
Figure 6).
\item \textbf{Own judging prompt} plus a cross-check with the original prompt
(Online Resource 1) on 3,000 judgments (original prompt scores $\sim$0.08 lower
but keeps all rankings --- see Figure 8).
\end{itemize}

\section{What each component does (along the pipeline)}
Running example: ``Who is Aescin contraindicated for?'' (QI288).
\begin{itemize}[leftmargin=*]
\item \textbf{Crawler:} 1,934 URLs $\rightarrow$ title, section tree, clean
text, source URL. 404/timeout/429 met with backoff retries + alternate
sources; only 1 URL abandoned after every documented attempt (recorded, never
faked).
\item \textbf{Cleaner:} strips ads/menus/recommendations/duplicates; keeps
titles, sections, URLs for traceability. Encoding audit: 0 mojibake across the
corpus.
\item \textbf{Chunker:} section-aligned splitting, long sections split further
while keeping parent metadata (91.9\% author-chunker match).
\item \textbf{Extractor:} each chunk $\rightarrow$ entities (name, 10+1 type,
description) + relations (source, target, keywords, description) + source
chunk id, temp 0, delimiter format.
\item \textbf{Index:} normalized matrices (768-dim for chunks/entities/
relations), BM25 over entity names and descriptions, two-way graph-to-chunk
maps (960\,MB, 8 files).
\item \textbf{Keywords:} 3--6 short $K_l$ terms + 1 $K_h$ sentence, lexical
fallback on LLM failure, memoized (1 call/question, 5x faster). Aescin example
$\rightarrow$ ``Aescin, contraindication, pregnant women, breastfeeding''.
\item \textbf{Anchors:} BM25 top-10 union dense top-10 outside BM25, threshold
filter, overlap bonus (entities found by both channels), top-15. Anchored:
``Aescin'', ``hypersensitivity'', ``pregnant women''.
\item \textbf{Edges:} one-hop neighborhoods around anchors, edge filter, joint
anchor-plus-query score, quota $m$, cap $N_{max}$ (at most 50 edges).
\item \textbf{Global/direct:} top-$n_g$ relations by broad keywords +
top-$n_s$ chunks by the raw question (safety nets outside anchor neighborhoods).
\item \textbf{Merge:} keep $\lfloor rn/2\rfloor$ per source, round-robin
interleave, dedup by id ($\sim$100-chunk pools).
\item \textbf{Reranker:} Qwen3-0.6B, automatic GPU/CPU pick, per-row fallback on
mid-run OOM, always exactly as many scores as documents (contract verified).
\item \textbf{Generator:} vLLM Qwen2.5-14B-AWQ temp 0, 400 tokens max.
\item \textbf{Judges:} Hit/MRR/nDCG (dual proxies), 4 RAGAS components, 4 dims
$\times$ 5 runs (minimal x3 $\rightarrow$ low x1 escalation: 116 vs 3,273
tokens, 28x cheaper; quota guard halts loudly), token/latency timers.
\item \textbf{Merger:} 8 tables + 11 figures; any missing file lands in a
pending list, never silently skipped (FINAL pending is empty).
\end{itemize}

\subsection{Table 4 -- Answer quality, the biggest gap, fully dissected}
Faithfulness 0.41 vs 0.89. Three measured layers, no guessing:
\textbf{Layer 1 (is the pipeline broken?):} our SHORT answers match the paper

chances to miss one). \textbf{Layer 2 (is our scoring wrong?):} proper two-step
scoring on identical data reaches 0.77 --- $\sim$75\% of the gap is our
one-step judging shortcut. \textbf{Layer 3 (what remains?):} a stricter judge
(solar vs GPT-5.5) plus noisier data (no GPT-5.5 access --- stated as a limit).
Answer relevancy 0.90, dim4 0.84, both high. Precision 0.86 vs 0.97: lean but
under-covering (recall 0.64 vs 0.94 --- leanness costs coverage;
standard-algorithm RAGAS gives ans.rel. 0.66 on 300 samples, ctx.rec. 0.64 on
275, ctx.prec. 0.86 on 46).

\section{Strengths, each with its number}
Paper: relevance control at the two most error-propagating stages (removing
anchors drops RAGAS most: 0.88$\rightarrow$0.72); lean contexts ($-$23\%
tokens) cutting ret+gen time (Table 6: 9.85s$\rightarrow$8.18s); honest
ablations (one module off each, baselines not sabotaged); public resources
(corpus + code + prompts --- this reproduction exists because of them).
Ours: Table-2 config lock 13/13 (any single wrong number surfaces instantly
in comparison); gates blocking corrupt numbers (fired twice, both correct
catches); dual-proxy absolute agreement; every substitution disclosed with
measured effect (flattering and unflattering alike); 43 fixes with
machine-verified evidence (log + file + assert, never blind).

%====================================================================
\section{Weaknesses and limits, each with its number}
Paper (Sec 6.3, their words, confirmed by our numbers): KG-quality dependence
(garbage in -- garbage out: our LCR 0.82 vs 0.91 shows it concretely);
fixed top-K budget (too much for easy questions -- our \texttt{dense\_only}
already reaches 0.90 -- too little for hard ones needing more evidence).
Ours: (1) manual gold replaced by proxies -- single-gold favors dense by
definition (measured 0.90 vs full 0.79; disclosed, never presented as paper
numbers); (2) stricter judge, esp.\ long answers (shortest quartile matches
the paper at exactly 0.89; longest only 0.53); (3) different standalone models
(references only, never ranked against each other or the paper); (4) noisier
extraction (LCR 0.82: the chunker merges small sections, root cause traced to
the cutter, not hand-waved); (5) faithfulness gap decomposed above (75\%
protocol, 25\% strictness+noise).

\section{Proposed fixes (evidence + real cost each)}
(1) \textit{Question-adaptive pipeline:} \texttt{dense\_only} nears full
(0.90 vs 0.79) $\rightarrow$ classify easy/hard up front, skip the graph for
easy, $\sim$10$\times$ cheaper, expect $\ge$95\% quality (easy questions need
no graph --- the very measurement above proves it). $\sim$4h GPU + $\sim$\$1
Solar (one new ablation column on ready infra, KG untouched). (2)
\textit{Rank-fusion instead of rerank-override:} reranking drags single-gold
Hit@1 $0.57\rightarrow0.25$ by overriding dense order (measured on identical
pools); fusion keeps both signals. $\sim$3h, no new answers needed. (3)
\textit{Sufficiency stopping} instead of fixed top-K --- the paper's own open
direction: stop when the supported-claim count saturates across 3 consecutive
chunks. $\sim$5h. (4) \textit{Length-controlled generation:} short answers
already match the paper (0.89); add a length cap and re-judge one arm.
$\sim$4h. Total Phase-2: $\sim$15h GPU + $\sim$\$5.
